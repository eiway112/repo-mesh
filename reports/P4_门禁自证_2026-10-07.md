## 八、v1.3 追记：同族判据缺陷的攻穿与修复（2026-10-07，脚本 v0.4.0）

起因：v1.2 修了 M10 的"本机存档行豁免盘符"缺陷，但**只审了被改的那一条判据**，未审"改动的连带面"。本次对全部判据重新做一遍攻穿，抓到 2 处缺陷——其中 1 处正是 v1.2 那次修改自己埋进去的。

### 8.1 缺陷 A：M2 放行 `~/` 本机符号（v1.1 遗留，非 v1.2 引入）

`check_m2` 原判定：`if not ("github.com" in loc or "~/" in loc or LOCAL_ARCHIVE_MARK in loc)`。
`~/` 与"（本机存档）"是**同一类问题的两种写法**——都只在本机成立、换机器即失效——但形式上像路径，登记人不会意识到自己写的是本机专属形式。实测注入 `~/.workbuddy/skills/some-skill/SKILL.md` → 退出码 0，放行。
修复：删除 `~/` 分支，并扩展识别 `gitee.com`（开源者用 Gitee 不是错，不该被误伤）。
**教训**：M2 与 M10 是同一诉求的两面（"外人能否复现" / "是否钉死在本机"），修M10 时必须同查 M2，否则口径分叉会从接缝长出新缺陷。

### 8.2 缺陷 B：M8 豁免过宽（v1.2 修改自己引入）

v1.2 修 M10 时，为处理"（本机存档）"标记行，把该标记加进了 `check_m8` 的豁免正则。**方向反了**：
M8 管的是"正文零领域名"，而台账里"（本机存档）"行恰恰最容易写出具体领域名（因为要说明是哪个工作区的哪个文件）。
实测注入 `…（本机存档）…（含{实例仓A领域}）` → 退出码 0，放行。
修复：豁免集收窄为"路径形态行"（含远端域名或盘符）。标记只承担"定位不可复现"的表达义务，不承担"内容可随意"的责任。
**教训（与v1.2 那次并列）**：两次缺陷同族同形——**豁免范围与风险方向相反**。加豁免前须问："这一类行是不是风险最高的那一类？"

### 8.4 CRLF 跨平台误报：处置与验证

**问题**：全局 `core.autocrlf=true` + 无 `.gitattributes` ⇒ Windows 检出把 LF 转 CRLF。原冻结基准以字节数+sha256 为主判据，跨机器算出不同值，**同一份内容被判成"文件被改"**。对开源仓致命：使用者克隆后基准全部对不上，冻结基准就失去作用。
**处置（两道独立防线）**：①仓内新增 `.gitattributes`（`* text=auto eol=lf`）从源头钉死行尾；②冻结基准主判据改为 **git blob 对象 id**（内容寻址，与平台/行尾/文件系统均无关），字节数+sha256 降为"行尾规范化后可比"的辅助读数。
**验证（跨平台恢复演练）**：`core.autocrlf=false` 克隆（模拟行尾不同的机器）后，四个冻结文件 blob id 与基准表 **4/4 逐条一致**，且检出工作树 CRLF=False。
**关键时序**：首次演练时 .gitattributes 尚未提交，克隆出来仍是 CRLF——**未入库的规则对他人无效**。这本身是"本地做了≠别人能用"的又一实例。

### 8.5 过程教训：同族错误第三次，且这次错在判定逻辑

本次自证脚本首轮报"0/5 一致"，但逐行看实测退出码全部正确（2/2/2/0/0）。排查：报告判对错的那行把**成功返回的 `(int, stdout)` 与错误返回的 `(str)` 都当二元组**处理，用长度判断导致成功路径被误判为无结论。改为按类型区分后 5/5 一致。
**这是本项目第三次犯同族错误**（前两次：注入锚串写错、校验脚本内千分位串与实际值不同口径）。三次形态一致：**阴性/异常读数先查自己的工具，再查被判据**——判据失效与工具出错在读数上无法区分，但工具出错更常见。
**追加纪律**：自证脚本的"期望 vs 实测"判定必须是独立于被测对象的一次计算；若判定逻辑与被测逻辑由同一段代码派生，它会同时掩盖双方。

### 8.6 版本漂移顺带修复

脚本 docstring 仍写 `v0.2.0`（v1.2 已升 v0.3.0 时只改了实现未改声明），冻结基准称 v0.3.0——判据表与代码不同步，属"检查器与它声称守护的性质脱节"同族。已一并修正为 v0.4.0，并在总则 §4.1 判据表同步 M2/M8/M10 三行的判据措辞（判据改了、表没改 = 制度与实现脱节）。

### 8.7 追加：远端真克隆恢复演练（v1.3 推送后）+ 一条被自己推翻的读数

**演练**：`git clone {本仓远端}`（真实远端）→ checkout v1.3。
-四个冻结文件 blob id 与基准表 **4/4 逐条一致**（`总则.md 863050e3…` 等）⇒ 异地副本可复现，冻结基准跨机器成立。
- 克隆副本上实跑门禁：退出码 0，M1–M10 全过 ⇒ 门禁在他人环境可跑（非仅本机可用）。
- 远端可见性：匿名访问 403，阳性对照（已知公开仓）200 ⇒ 私有性确认。

**须纠正的一处读数（重要）**：本次演练中我一度用 `grep -c $'\r'` 得出"克隆出来仍是 CRLF，.gitattributes 没生效"，
并据此怀疑规则被`core.autocrlf` 覆盖。**该读数是错的**——改用 Python 二进制读（经 `cygpath -w` 换真实Windows 路径）后：
`总则.md CRLF=0 裸LF=255`、`README.md CRLF=0 裸LF=62`，**行尾处置实际是成功的**。
两处工具坑叠加：`grep -c` 判 CR 不可靠（本机环境事实 skill 早有此条，我没避开）；且 Bash 的 `/tmp` 是 MSYS 挂载点，
原生 Python 看不到它，须 `cygpath -w` 换路径才能读到真实文件。
**已坐实的正面结论**：仓内 `.gitattributes`（`eol=lf`）优先级**高于**全局 `core.autocrlf=true`，
`git check-attr eol -- 总则.md` 返回 `lf` 且实测检出为 LF。**唯一前提是该文件已提交入库**——未提交时对他人无效。
**这是本轮第四次同族错误**（前三次见8.5），形态仍是"读数异常先查自己的工具"。已把两处工具坑与该正面结论
写入本机环境事实 skill v2.9.0，避免下次重犯。

## 九、M11 全仓开源卫生判据（新增，脚本 v0.5.0）

**为什么加**：M9/M10 只扫总则正文（`总则.md` 一份文件），而 `reports/` 与立项策划方案里的本机路径与真实姓名完全在机检盲区内——开源就会泄漏本机目录结构与维护者身份。此前只有 README 里一句"发布前记得脱敏"，属**无判据支撑的纪律**，实际会被忘记。

**新增准入三问自查**（维护者裁定后落地）：
1. 有调度/触发点？——有，每次门禁实跑，与 M9/M10 同批。
2. 触发时让谁做什么不同的事？——维护者从"发布前记得脱敏"变为"脱敏不了就进不了公开仓"。
3. 有没有一条旧的因此可删？——T5 第 4 条从"待办"变为"机检可查"，该条本身保留（机检只管形式，内容可公开性仍属人裁）。

### 9.1 判据设计要点

- **黑名单单一来源**：与 M9/M10 共用 `PERSON_NAMES` 与同一条盘符正则，**不得各写一份**。
- **扫描范围显式**：`reports/*.md` + 仓根策划方案，**不递归全仓**（递归会把冻结对象卷进来，而冻结对象由 M9/M10 负责，职责不重叠）。
- **豁免只认显式占位符**（`{本机路径}` / `X://…`）；**「（本机存档）」标记不是豁免理由**——它是给人看的说明，不是脱敏。
- **P-01 兜底**：两类对象都不存在时报FAIL"无对象"，退出码 2，不静默通过。

### 9.2 初版即抓到自身缺陷（本节最值得记）

M11 初版盘符正则误写为 `r"[A-Za-z]:\\\\"`（匹配**两个连续反斜杠**），而文件里是单个。
**表现**：首跑只报人名、盘符一条不报，共 13 项——若只看"有没有报错"会以为判据在工作。
**暴露的机制问题**：这不是转义手误，而是**判据分叉的代价**——M10 与 M11 各自持有一条本该相同的正则，
写错一条，另一条仍然"看起来在查"。**判据一旦复制，就有了独立漂移的可能。**
**修法**：不再各写一条，改为同源；并在注释里写明"本条初版误写"的教训，让后来者知道这里曾出过事。
**这已是本项目第五次同族错误**（见8.5），形态仍是"分叉处与打岔处"。

## 十、M1 第四章子节双向差集校验（v1.5，脚本 v0.6.0）

**起因**：新增 4.2.1「待决事项登记」后做例行核验，发现一个**正向全绿却长期存在的判据缺口**。

### 10.1 缺陷：M1 声明了检查，实际从未执行

`check_m1` 原实现只遍历 `ANCHORS`（5 个一级章节），验证每个标题行恰好出现一次。
第四章的子节清单 `FOURTH_SUBSECTIONS` 虽然在脚本里定义，**但只被M7 消费，且M7 是"节存在才查"**——
即：某节没登记进 `FOURTH_SUBSECTIONS`，M7 就根本不查它；而M1 压根不管子节。

后果：新增 4.2.1 与早已存在的 4.6，**两节从未被任何判据覆盖**，而门禁全绿（exit 0）。
这比"判据查不出"更严重——它是**"声明了检查、实际没执行"**：维护者读脚本会以为结构被守着。
按项目铁律"每个闸门要证明坏的会被拦"（P-03），正向全过完全不能证明这条判据称职。

### 10.2 修法：双向差集，不是补清单

直觉做法是把 4.2.1 与 4.6 补进 `FOURTH_SUBSECTIONS`——**那样只是把一份手工清单补全，下一个人加节时还会重犯**。
本次改为校验两个方向：

| 方向 | 抓什么 |
| --- | --- |
| 声明 ⊆ 实际 | 脚本清单里的节在文档中不存在（清单漂移） |
| 实际 ⊆ 声明 | 文档里的节没进脚本清单（**新节漏登记——这半边才是能自动抓出复发的那一半**） |

同时加一条P-01 式兜底：解析不到任何第四章子节时直接 FAIL 并返回，**防"正则失效导致全绿"**——
否则文档格式一变，正则匹配 0 个，差集为空，反而会 PASS。

### 10.3 攻穿自证（4/4 一致）

| # | 用例 | 期望 | 实测 | 结论 |
| --- | --- | --- | --- | --- |
| 1 | 【旧缺陷回归】新增 `### 4.2.9` 但不登记 | FAIL[M1] 报 4.2.9 | 2，报 4.2.9 | 原缺陷已堵 |
| 2 | 【反向】文档中真删掉 4.6 整节 | FAIL [M1] 报清单漂移 | 2，报 4.6 漂移 | 另一方向也咬人 |
| 3 | 【零误报】含 4.2.1 与多行表格的正常内容 | PASS | 0，零 FAIL | 小节号与表格不误伤 |
| 4 | 【阴性对照】未改动副本 | PASS | 0 | 判据无副作用 |

用例 3、4 是合法样本：只验攻穿会把"过度收紧"放过去。

### 10.4 过程中两次自查（都不是判据问题）

1. **首跑报"4.4.2.1 / 4.4.6"** —— 我在报错文案里多写了 `4.` 前缀，而变量本身已含`4.`。判据报的编号是对的，**是我的显示层制造了假象**。已修。若当时只看报错就"修"判据，会把对的改错。
2. **用例 2 首轮"不一致"** —— 根因是我的注入没生效：只改了 4.6 的标题文字、编号 4.6 仍在，M1 正确地认为它存在。改为真删整节后通过。**又一次"阴性读数先查自己的工具"。**

另：自证脚本首跑即崩（`FileNotFoundError: 总则.md`），根因是脚本用 `os.path.abspath(".")` 定位仓根，而它是被**绝对路径**调用的、cwd 在 `%TEMP%`。已改为硬编码仓根 + `assert` 前置校验。
**教训**：临时验证脚本的路径基准须与调用方式一致；用相对 `.` 定位是这类脚本最常见的自伤方式。
